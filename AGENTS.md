# Repository Guidelines

## Project Structure & Module Organization

- `src/` contains the static web UI. Edit `app.js`, `hud.js`, the HTML entry points, and their paired CSS files here.
- `src/app.bundle.js` and `src/hud.bundle.js` are generated by esbuild; edit their source modules and rebuild instead of changing bundles directly.
- `src-tauri/src/lib.rs` owns application state, status polling, notifications, tray behavior, Tauri commands, and Rust unit tests. `main.rs` is only the executable entry point.
- `src-tauri/tauri.conf.json` defines windows and packaging; `capabilities/default.json` defines frontend permissions. Icons live in `src-tauri/icons/`.
- `dist/` and `src-tauri/gen/` are generated outputs. Avoid hand-editing them.

## Build, Test, and Development Commands

- `pnpm install` installs JavaScript and Tauri CLI dependencies from `pnpm-lock.yaml`.
- `pnpm build:web` bundles `src/app.js` into `src/app.bundle.js`.
- `pnpm dev` rebuilds the web bundle, serves `src/` on port 1420, and launches the Tauri app.
- `pnpm build` creates release bundles through Tauri.
- `cd src-tauri && cargo test` runs Rust unit tests.
- `cd src-tauri && cargo fmt --check` and `cargo clippy --all-targets -- -D warnings` check Rust formatting and diagnostics.

## Coding Style & Naming Conventions

Use two-space indentation in JavaScript, JSON, HTML, and CSS; let `rustfmt` format Rust. Follow existing conventions: `camelCase` for JavaScript functions and variables, `snake_case` for Rust functions and modules, and `PascalCase` for Rust types. Keep Tauri commands small and place shared monitoring logic in focused Rust helpers. Preserve the existing Chinese UI copy and comments unless a feature requires new terminology.

## Testing Guidelines

Add Rust tests in the `#[cfg(test)]` module near the behavior under test, using descriptive `snake_case` names. There is no JavaScript test runner or formal coverage threshold yet. For UI changes, run `pnpm dev` and manually verify the main window, tray actions, HUD, configuration persistence, status refresh, and notification transitions.

## Commit & Pull Request Guidelines

This checkout has no Git metadata, so repository-specific commit history cannot be verified. Use short imperative subjects, preferably Conventional Commit prefixes such as `feat:`, `fix:`, or `chore:`. Pull requests should explain user-visible behavior, list validation commands, note permission or configuration changes, link relevant issues, and include screenshots for main-window or HUD changes.

## Security & Configuration Tips

Do not commit tokens, private endpoints, logs, or local configuration. Treat changes to `capabilities/default.json`, external URLs, autostart, and notification permissions as security-sensitive and call them out during review.
